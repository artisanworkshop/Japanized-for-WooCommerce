## 検証した事実（指摘なし）
- `[A-Za-z0-9_-]` の `-` は文字クラス末尾なのでリテラル。`/` `?` `#` `%` 空白 タブ CR は新正規表現でも拒否（php -r で実測）
- `rawurlencode( '-_.~' )` → `-_.~`。コメントの RFC 3986 unreserved / `rawurlencode()` の記述は正しい
- 新テストは旧正規表現で 4 件（ハイフン 3 ケース + issue シナリオ）が失敗し、新正規表現で全 20 件通過（変異確認済み）
- `pre_http_request` は `WP_Http::request()` 内で `wp_http_validate_url()` より前に走る。記録される URL は関数が組み立てたものそのもの。モック配列は `wp_remote_retrieve_response_code()` / `wp_remote_retrieve_body()` の期待形に一致
- E2E 検証テストは `paidy_verify_payment_for_order()` の全チェック（id 一致・order_ref 一致・amount 差 < 0.01・status 許可リスト）を現実的な値で通す

## 指摘
### [R1-1][Low][includes/gateways/paidy/class-wc-gateway-paidy.php:1162]
PCRE の `$` は末尾の `\n` 1 文字の直前にもマッチするため、`"pay_abc\n"` が旧・新どちらの正規表現も通過する（実測: old=1 new=1、`D` 修飾子付きで 0）。実害なし: thank-you 経路は `sanitize_text_field()` が改行を除去し、Webhook 経路でも `rawurlencode()` が `%0A` に符号化したうえで `paidy_info['id']` との厳密比較で不一致になる。ただし今回書き換えたコメントの「whitespace are still rejected」が末尾改行には当てはまらない。旧正規表現から引き継いだ性質だが、この行を書き換えているので記録。
**修正方針:** `/^pay_[A-Za-z0-9_-]+$/D` にし、コメントに `D` の意図を 1 句添える。

### [R1-2][Low][tests/Unit/test-paidy-payment-id-format.php:138]
`'newline' => "pay_abc\nx"` は改行の後ろの `x` で弾かれており、改行そのものの拒否は検証していない。R1-1 を固定するケースがない。
**修正方針:** `'trailing newline' => array( "pay_WD1KIj4AALQAIMtZ\n" )` を追加する（R1-1 とセットで変異確認）。

### [R1-3][Low][tests/Unit/test-paidy-payment-id-format.php:133-144]
`invalid_payment_id_provider()` の `=>` 揃えが全行 1 桁ずれ（WordPress 標準で `Array double arrow not aligned correctly` 警告 12 件、phpcbf で自動修正可）。`.phpcs.xml.dist` が `/tests/` を除外しているため `composer lint` / CI では検出されない。
**修正方針:** `vendor/bin/phpcbf --standard=WordPress` を当該ファイルに当てる。
