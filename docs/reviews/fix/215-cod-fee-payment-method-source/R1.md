## 指摘
### [R1-1][High][includes/class-jp4wc-cod-fee-handler.php:167, 256-265]
Store API の別名ルートで、正当な注文が 409 `jp4wc_gateway_fee_mismatch` になる。チェックアウトの判定が `/wc/store/v1/checkout` の前方一致だけで、WooCommerce が同じハンドラーを登録しているバージョンなしの `wc/store` や、大文字小文字の違うパス（WordPress のルート照合は大文字小文字を区別しない）では `payment_method` を捕捉できない。手数料はセッション値で計算され、ガードが「計算に使ったゲートウェイ ≠ 注文の支払い方法」で拒否する。セッションに選択が無い状態で `POST /wc/store/checkout`（`payment_method=bacs`）を送ると 409 になることを実行で確認。2.9.16 では `jp4wc_gateway_id` が空ならガードを素通ししていたので退行。
**修正方針:** ルート判定を `wc/store` と `wc/store/v1` の両方・大文字小文字無視にする。ガードは不一致のどちらかが cod / cod2 のときだけ拒否する（手数料の判定が変わらない不一致は通す）。あわせて、手数料計算の途中で行っていた「利用可能なゲートウェイか」の確認をやめる（WooCommerce が同じリクエストを自分で検証・拒否する。計算途中はカート合計が 0 で、可否フィルターの結果が確定後と食い違うとセッション値へフォールバックして同じ 409 を招く）。

### [R1-2][Medium][includes/class-jp4wc-cod-fee-handler.php:165, 208]
static の状態がリクエスト単位になっていない。`$request_payment_method` は毎リクエスト null に戻すが、`$fee_basis_gateway_id` は戻さない。同一プロセス（Store API のバッチ）で `PUT /checkout`（bacs）→ `POST /checkout/<id>`（既存注文の支払い、cod）と続くと 409 になることを実行で確認。逆に、毎リクエスト単純に null へ戻す方式は、ルートの処理中に内部で別の REST リクエストが dispatch されると外側の値を消す。
**修正方針:** チェックアウトリクエストの開始時（`rest_request_before_callbacks`）に直前の状態を退避して両方を初期化し、終了時（`rest_request_after_callbacks`）に戻す。

### [R1-3][Medium][tests/Unit/test-jp4wc-cod-fee-gateway-validation.php]
テストがハンドラーのメソッドを直接呼ぶだけで、`init()` のフック登録も実際の dispatch も通らない。2 つのフック登録を外しても 21 件すべて成功し、その状態では「拡張エンドポイントに bacs → 代引きで注文」が手数料なしで成立する（2.9.16 で塞いだ穴の再発を検知できない）。
**修正方針:** Store API を実際に dispatch する統合テストを追加する（拡張エンドポイント → 注文確定の両方向、ブロック自身の PUT の応答、別名ルート、同一プロセス内の後続リクエスト）。

## 確認して問題なかった点
- 拡張エンドポイントに bacs → `POST /checkout` を cod: 注文は cod、手数料付き。逆方向（cod → bacs）は手数料なし
- 偽 ID・配列の `gateway_id` は無視され、`chosen_payment_method` は変わらない
- `PUT /checkout?__experimental_calc_totals` の応答の fees は、セッションが古くてもリクエストの支払い方法に一致（両方向）
- 10.9 より前のドラフト注文を使う PUT / POST（9.8.1 / 10.7.0 のソースで確認）、クラシックの `update_order_review` / `wc-ajax=checkout`、管理画面・cron
- `chosen_payment_method` を読む WooCommerce 側のコードへの影響（WooCommerce 自身の PUT が書く値と同じ扱い）
