## 確認したこと
- 申込を送る経路はすべて、保存済みの hash と同じ値を 1 回だけ送る: 追加経路の step 2(初回 / hash あり / 空の行)、更新経路の 1 → 2、追加経路の step 1 → 入れ子の `update_option()` → 入れ子の `add_option()` → step 2(サブエージェントの調査用テストで確認。main ではこの経路が**初回申込でも** `site_hash` = null を送っていた)
- `add_option()` → `update_option()`: 行が無いときは `update_option()` が `add_option( $option, $value, '', null )` に委譲するので autoload は従来と同じ(WP 7.1.3 の option.php と DB で確認)。`paidy_site_hash` の保存で発火する `add_option` / `updated_option` は、このクラスのハンドラが先頭でオプション名を確かめて return するので再入しない
- テストはコンストラクタで登録された実際のフックを通る。プラグイン読み込み時の wizard インスタンスは `woocommerce_paidy_settings` が無い時点で作られるのでフックを登録せず、二重送信は起きない。HTTP はすべて `pre_http_request` で止めている
- フル 358 件 OK(新規 4 件)。Paidy 関連テストのランダム順 2 回も OK
