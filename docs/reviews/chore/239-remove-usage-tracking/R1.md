## 確認して問題がなかったこと
- 削除したクラス・メソッド・`jp4wc_tracker_*` フック・`wc4jp-tracking`・設定キー `tracking`・`usageTracking` の参照は、片付けのコード(`class-jp4wc-install.php`、`uninstall.php`)以外に残っていない。jp4wc-pro も全履歴で使っていない(`jp4wc_pro_tracking` は配送追跡で別の機能)
- 2.9.16 のコードが送信していた経路は `jp4wc_installed` / `jp4wc_updated` / WP-Cron の 3 つだけで、HEAD にはどれも残っていない
- `remove_usage_tracking()` は `install()` の中なので、新規インストールでも更新でも走る。`is_installing()` で早く抜けても `jp4wc_version` が更新されないため、次のリクエストでやり直される
- 削除したクラスの `wp_cache_set()` はすべて TTL 付き(600 秒または 1 時間)で、そのまま期限切れになる。transient は使っていなかった
- 設定 API の許可リストから `tracking` が消えたので、古い JS から送られても保存されない
- 新しいテスト 5 件は、変更を戻したコードでは 5 件ともアサーションで失敗する(実装者とサブエージェントの両方で確認)。逆順・乱数順でも新しいテストは通る(落ちるのは backlog R1-X4 の `JP4WC_Address_Email_Test` だけ)
- PHPUnit 363 件 OK。lint は 94 errors / 12 warnings(main は 97 / 30。変更したファイルの指摘は既存のものだけ)

## Low(backlogへ)
- [R1-L1][Low][includes/class-jp4wc-install.php:`remove_usage_tracking()`、uninstall.php] 2.6.10〜2.6.19 は別名の WP-Cron イベント `wc4jp_tracker_send_event` を予約していた(`git show 2.6.19:includes/class-jp4wc-install.php` の 82 行目)。2.6.20 でフック名が変わってから、このイベントを消したバージョンはない。リスナーが無いので送信は起きないが、cron 配列に残り続ける。`wp_clear_scheduled_hook( 'wc4jp_tracker_send_event' )` を足せば片付く
- [R1-L2][Low][includes/class-jp4wc-install.php:`remove_usage_tracking()`] 片付けはバージョンの条件なしで、以後のすべての更新で走る。後継の機能が同じ名前(`wc4jp-tracking` / `jp4wc_tracker_send_event`)を使うと、更新のたびに同意と予約が消える。後継の機能ではこれらの名前を再利用しない(または片付けを `version_compare( $previous_version, '2.9.17', '<' )` に限る)
- [R1-L3][Low][.wordpress-org/screenshot-1.png] スクリーンショット 1 の下部に「使用状況の追跡 / 追跡(ON)」パネルが写ったまま。キャプションからは外した。デプロイの `10up/action-wordpress-plugin-deploy` は既定で `.wordpress-org` を wp.org の assets に同期するので、タグの push でこの画像もそのまま公開される。一般設定タブを撮り直して差し替える
- [R1-L4][Low][tests/Unit/test-jp4wc-usage-tracking-removal.php:7, 61] コメントが実際と合わない。7 行目の「and weekly when enabled」は、保存値 `'1'` と判定値 `'yes'` が食い違っていたため毎週の送信は動いていなかった。61 行目の「An update runs on an admin request」は、`check_version()` が `init` でどのリクエストでも走るので不正確(`require_once` の実際の目的は、変更前のコードが読み込まずに呼ぶ `get_dropins()` で fatal にならず、アサーションまで到達させること)
