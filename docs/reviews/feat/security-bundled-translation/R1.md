## 指摘
### [R1-1][Medium][tests/Unit/test-jp4wc-bundled-translation.php]
テスト用の言語パックは `__()` の 1 件しか訳さないので、`_n()` と `_x()` で言語パックの訳が勝つことを確かめていない。`jp4wc_bundled_plural_translation()` の未翻訳判定を消して常に同梱の訳を返しても、全テストが通る（サブエージェントが worktree で実測）。
**修正方針:** パックに複数形と文脈付きのエントリを足し、ラッパーの中でも言語パックの訳が返ることを assert する

### [R1-2][Medium][includes/admin/class-jp4wc-security-api.php `with_bundled_translation()`]
REST のクロージャがメインファイルの `jp4wc_with_bundled_translation()` を呼ぶが、この関数は 3.0.0 のメインファイルにしか無い。2.9.20 の `JP4WC::includes()` は 3.0.0 の `class-jp4wc-admin-settings.php` を読み（そのファイル自身のコメントのとおり）、それがファイル先頭で security-api を読んで `rest_api_init` でルートを登録する。「ルートの 2 ファイルが旧版、includes/ が新版」の更新中のリクエストで `/jp4wc/v1/security/*` を呼ぶと未定義関数で Fatal。そのルートを呼ぶのは 3.0.0 の Security タブだけなので実害の見込みは小さいが、CLAUDE.md の「includes/ のファイルは前の版の includes() に読まれうる」に反するので Low から Medium に上げた。通知クラスは 3.0.0 以降の `class-jp4wc.php` と `uninstall.php`（`admin_notices` は発火しない）しか読まないので対象外。
**修正方針:** クロージャで `function_exists()` を見て、無ければ callback を直接呼ぶ

## 確認して問題なかったこと
- エントリの引き方: `WP_Translation_File_MO::parse_file()` は複数形を単数形だけのキーで登録し、文脈は `ctx\4text`。`translate()` の値は `\0` 連結で、先頭が単数形の訳（Controller の `translate()` も `entries[0]`）
- `_n()` の未翻訳判定は `WP_Translations::translate_plural()` の英語ルールと一致。複数形の番号は同梱ファイルの Plural-Forms（ja は nplurals=1）から選ぶ
- フィルターの引数: `gettext_` 2 個 / `gettext_with_context_` 3 個で文脈を取り違えない。`_x()` / `esc_attr_x()` / `translate_nooped_plural()` に効き、`_nx()` には効かない（実測）
- 再帰なし: フィルター内の `determine_locale()` / `get_user_locale()` / `WP_Translation_File` はこのドメインの翻訳関数を呼ばない。`WP_Locale_Switcher` の `determine_locale` フィルターにも従う
- REST: `respond_to_request()` と `rest_send_allow_header()` は `call_user_func( $cb, $request )`。OPTIONS 200・`Allow: GET` を実測。`get_data_for_route()` は callback を出さない。WooCommerce にも handler の callback を調べる処理は無い
- 性能: 同梱の .mo（98KB）の解析は約 0.46ms で、言語パックに無い文字列があったときに 1 リクエスト 1 回。en_US など同梱ファイルの無いロケールでは何もしない
- 22 件すべてに同梱の ja .mo の訳がある。2.9.20 以降に変わった他の PHP ファイルに新しい翻訳呼び出しは無い
