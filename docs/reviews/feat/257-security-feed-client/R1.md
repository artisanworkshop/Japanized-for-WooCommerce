## 指摘
### [R1-1][High][includes/class-jp4wc-security-feed.php:281-299（sync）/ rescan]
同期（数秒〜数十秒）の最中に設定画面で無効化すると、`purge()` が消した state・照合結果・ファイルを、同期が開始時に読んだ値で書き戻す（`rescan()` の `is_enabled()` もプロセス開始時の alloptions の `'1'` を読む）。purge が次回の日次イベントも消しているので次の同期は来ず、`ensure_schedule()` も「無効かつ未予約」では片付けないため、数十 MB のファイルと2つのオプションが無効のまま残り続ける。readme の「無効化でデータを削除」と食い違い、CLAUDE.md の #275 の落とし穴に当たる。
**修正方針:** state・照合結果を書く直前に設定を DB から読み直し、無効なら `purge()` して終える。競合を再現するテストを足す。

### [R1-2][Medium][uninstall.php:39-43]
マルチサイトでは各サイトが自分の cron・オプション・`uploads/sites/N/jp4wc-security/`（数十 MB）を持つが、アンインストールは今のサイトしか片付けない。
**修正方針:** 片付けを `JP4WC_Security_Feed::uninstall()` にまとめ、マルチサイトでは全サイトを `switch_to_blog()` して purge する。

### [R1-3][Medium][uninstall.php:39-43]
受け入れ条件「uninstall.php で cron・オプション・`uploads/jp4wc-security/` を片付ける」にテストが無い（uninstall.php はグローバル関数を宣言するので1プロセスで1回しか読めない）。
**修正方針:** R1-2 の `uninstall()` をテストする。

## 対象外指摘（差分範囲外）
- [R1-X1][Medium][plugins/artws-security-hub/includes/class-artws-sec-feed-publisher.php:138] サーバーが各 vuln ファイルに生成のたびの `generated_at` を書くため、データが同じでも gz の sha256 が毎日変わる。クライアントの「sha256 が同じなら取りに行かない」が実運用で効かず、全サイトが毎日3ファイル（数 MB）を取得する。内容が同じなら前回の gz をそのまま使う、またはファイルの `generated_at` をデータの更新時刻にする
- [R1-X2][Low][uninstall.php（既存部分）] 既存のオプション削除もマルチサイトの各サイトを回らない
