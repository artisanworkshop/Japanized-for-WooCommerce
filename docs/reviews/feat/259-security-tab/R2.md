## 指摘（R1 の修正で新たに混入したもの）
### [R2-1][Medium][includes/class-jp4wc-security-feed.php `request_recheck()`]
R1-2 で足した `keep_written_data()` は設定行が無いと「オフ」とみなして purge するが、`is_enabled()` は行が無ければ「オン」。設定行を手で消したサイトで再チェックを押すと、データと SYNC が消えて 409 が返る。
**対応:** 先頭で `start_run()`（`sync()` / `rescan()` と同じ）。`test_rescan_without_setting_row` を追加し、行を外すと失敗することを確認（ccaa16a）。

### [R2-2][Low][includes/class-jp4wc-security-feed.php `recheck()`]
依頼時刻を `wp_cache_delete()` だけで読み直しており、`notoptions` から外していない（CLAUDE.md の規則）。
**対応:** `notoptions` からも外す。`test_recheck_reads_the_request_from_the_database` を追加し、どちらの行を外しても失敗することを確認（ccaa16a）。

### [R2-3][Low][class-jp4wc-security-api.php `RECHECK_RUNNING_FOR` / class-jp4wc-security-feed.php `request_recheck()` の docblock]
完了判定が「findings の checked_at」のままの説明。
**対応:** 「再チェックが実行を記録するまで（RECHECK_DONE_OPTION）」に修正（ccaa16a）。

## 確認したが指摘しない点（サブエージェント）
- 実行中の 2 回目の依頼は新しいイベントになり、先の実行が古い時刻を書いても pending は続く。cron ロックを超えて並行した場合の done_at の後退は、画面の待ち時間切れ（3 分）だけで済む
- 409 の経路は何も残さない。無効時の `recheck()` の purge は `sync()` と同じ扱い
