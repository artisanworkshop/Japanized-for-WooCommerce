## 指摘
### [R1-1][Medium][includes/admin/class-jp4wc-security-api.php:240 / SecuritySettings.js（waitForRecheck）]
再チェックの完了を `checked_at >= requested_at` で判定しているが、`checked_at` は rescan の開始時刻なので、再チェックの前に同じ cron 実行で走る自動の RESCAN（プラグイン有効化などで予約）や期限切れの SYNC でも条件を満たす。それらは probe の保存結果（最長 12 時間前）を使うため、画面は古い結果で「再チェックが終わりました」を出してポーリングを止める。
**修正方針:** `recheck()` が開始時に読んだ依頼時刻を、終了後に専用オプション（`jp4wc_security_recheck_done_at`）へ書き、`pending` と画面の完了判定をその値で行う。

### [R1-2][Medium][includes/class-jp4wc-security-feed.php:323-333, 352-355]
`request_recheck()` は REST ハンドラー冒頭の `is_enabled()`（プロセス内のキャッシュ）だけを見て RECHECK のオプションとイベントを書き、書いた後に設定を確かめない。別のリクエストで OFF→purge が間に入ると行とイベントが残り、`recheck()` は無効なら何もせず戻るため OFF の間ずっと残る（CLAUDE.md の「書き込みの後に確かめる」規則）。
**修正方針:** `request_recheck()` の書き込み後に `keep_written_data()` を呼び、purge されたら 0 を返して API は 409。`recheck()` も無効なら `sync()` と同じく purge する。
